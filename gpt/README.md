# MiniGPT-RU — свой GPT-трансформер на ~30M параметров

Полный пайплайн своей языковой модели **с нуля, на PyTorch, без внешних ML-библиотек**:
свой BPE-токенайзер → современная архитектура декодера → агрессивный оптимизатор (Muon) →
pretrain → SFT на диалогах → терминальный чат с KV-кэшем.

```
Вы> Что такое трансформер?
Модель> Трансформер — это архитектура нейронной сети, предложенная в 2017 году.
        Её главное отличие — механизм внимания.
```
*(реальный вывод демо-модели из этого репозитория, см. «Быстрый старт»)*

## Честно о том, что получится

Это важно прочитать до обучения, чтобы ожидания совпали с результатом.

| Бюджет | Что умеет модель |
|---|---|
| 30M параметров + **5M токенов** | узнаваемые русские слова, обрывки фраз из корпуса. Это уровень «проверить, что пайплайн работает». |
| 30M + **600M токенов** (Chinchilla-оптимум) | грамматика и стиль русского языка, связные предложения, отдельные заученные факты. Перплексия ~20–30. |
| 30M + **10–50B токенов** | лучший возможный результат для этого размера: беглый русский, простые рассуждения, факты, которых много в корпусе. |
| 30M + SFT на **5–50k качественных диалогов** | уверенно отвечает **на те типы вопросов, что были в данных**, в правильном стиле и формате. |

**Чего не будет ни при каком объёме данных:** свободной эрудиции и рассуждений
уровня GPT-4/Claude. Знания физически хранятся в параметрах: 30M параметров —
это примерно 20–30 МБ «памяти» в fp16. Большая модель умнее не потому, что
лучше обучена, а потому что в неё помещается больше.

**Реальный замер в этом репозитории** (CPU, 2 ядра): 1.84M параметров, 2.05M
токенов настоящей русской литературы и новостей → `val loss 3.454 (ppl 31.6)`,
4 800 ток/с обучения, 7 минут. Генерация:

```
> Однажды весной лицо по крайней стороны и все же как в себе, что я все и как будто он было
> Президент заявил, что в чем лицо ли вы не имею как у меня в этом жизни, и в доме время для
```

Словоформы и синтаксис русские, смысла нет — это и есть потолок при 2M токенов.
Чтобы получить связный текст, нужны сотни миллионов токенов и модель покрупнее.

**Кривая текущего прогона** (`small`, 12.88M параметров, тот же корпус,
1 822–1 889 ток/с, AdamW + WSD + EMA):

| Шаг | Токенов | train loss | val (raw) | val (EMA) | ppl |
|---|---|---|---|---|---|
| 2 000 | 3.07M | 3.4794 | 3.4737 | 3.5599 | 32.3 |
| 4 000 | 6.14M | 3.1803 | 3.1946 | 3.1103 | 22.4 |
| 6 000 | 9.22M | 3.0810 | 3.0594 | 2.9843 | 19.8 |
| 8 000 | 12.29M | 3.0238 | 3.0292 | 2.9238 | 18.6 |
| 10 000 | 15.36M | 3.0092 | 2.9796 | 2.8432 | 17.2 |

**Отжиг** (annealing) из той же точки: продолжение с шага 10 000, спад lr
1.5e-3 → 1.5e-4 за 4000 шагов, итого 21.5M токенов:

| Шаг | val (raw) | val (EMA) | ppl |
|---|---|---|---|
| 10 000 (до отжига) | 2.9796 | 2.8432 | 17.2 |
| 12 000 | 2.8798 | 2.8031 | 16.5 |
| 13 000 | 2.8203 | 2.7711 | 16.0 |
| **14 000** | **2.7713** | **2.7539** | **15.7** |

Зачем это нужно и почему это дёшево. В длинном прогоне `decay_start =
steps − steps/5`, то есть при `--steps 60000` спад lr начался бы только на
шаге 48 000 — одиннадцать часов работы просто держали бы lr высоким. Поэтому
raw-веса и легли на полку (3.0594 → 3.0292 → 2.9796), пока EMA продолжала
падать. Отжиг из готового чекпойнта снимает этот эффект за час:

```bash
# из чекпойнта стабильной фазы, без потери возможности продолжить длинный прогон
cp out/small-long/ckpt.pt out/small-anneal/ckpt.pt
python train.py --preset small --data-dir data/prepared_real --out out/small-anneal \
    --resume --steps 14000 --decay-len 4000 --optimizer adamw --lr 1.5e-3 --schedule wsd
```

Правило: **если останавливаете прогон раньше `--steps`, сначала отожгите**.
Остановка на стабильной фазе выбрасывает заметную часть качества.

Два наблюдения, которые стоит запомнить:

* **EMA обгоняет raw не сразу, но потом уходит в отрыв.** На шаге 2000 EMA хуже
  (3.5599 против 3.4737) — скользящее среднее ещё не отошло от инициализации,
  горизонт EMA ~1000 шагов. Дальше разрыв только растёт: 3.1103/3.1946 →
  2.9238/3.0292 → 2.8432/2.9796. Raw-веса к шагу 8000 почти перестали
  улучшаться (3.0594 → 3.0292 → 2.9796), а EMA продолжает падать. Поэтому
  `best_source` записывается в чекпойнт, и `load_any` берёт веса по нему.
* **Большая модель обгоняет маленькую не мгновенно.** `tiny` на 2.05M токенов
  давал ppl 31.6; `small` на 3.07M — 32.3, то есть на пересечении. Выигрыш от
  ёмкости появляется только когда токенов достаточно: к 6.14M уже ppl 22.4.

Для сравнения, шаг 4000 (ppl 22.4):

```

```

**Реалистичная цель для 30M:** модель, которая *ощущается* умной на своей узкой
задаче — отвечает по вашим документам, в вашем стиле, без воды. Достигается это
не «хитрой архитектурой», а тремя вещами:

1. **Хороший токенайзер** для русского (больше словарь → больше смысла в 30M параметров).
2. **Много данных pretrain** (стиль и грамматика) — минимум 1–5B токенов, лучше 10B+.
3. **Дистилляция в SFT**: несколько тысяч диалогов, где ответы сгенерированы
   большой моделью (любой API) на *ваших* темах. Это и есть главный источник
   «ума» у маленьких моделей — так сделаны все маленькие чат-модели.

## Архитектура

Декодер GPT, но с тем, что реально даёт качество на малом размере:

| Приём | Зачем |
|---|---|
| **Pre-RMSNorm** | устойчивее LayerNorm на bf16, дешевле |
| **RoPE** | порядок токенов через поворот q/k; контекст на инференсе не ограничен обучением |
| **GQA** (8 q-голов / 4 kv) | −25% параметров в k/v и вдвое меньше KV-кэш |
| **QK-Norm** | нормализация q,k перед RoPE — не «взрываются» attention-логиты |
| **SwiGLU MLP** | стабильно лучше GELU-MLP при том же числе параметров |
| **Скользящее окно + глобальные слои** | 2/3 слоёв видят только 1024 последних токена, каждый 3-й — весь текст. Контекст 4k без квадратичной цены |
| **Связанные веса** | эмбеддинг == голова: экономит `vocab × n_embd` (6.3M из 30M) |
| **Уменьшенный init выходных проекций** | остаточный поток не растёт с глубиной |
| **Опц.: logit soft-capping, z-loss** | страховка от расходимости на bf16 |

### Оптимизация

* **Muon** для всех матриц внутри блоков: момент градиента ортогонализуется
  итерацией Ньютона–Шульца (5 шагов, без SVD), поэтому за шаг обновляются **все**
  направления, а не только главные. Эмбеддинги и RMSNorm остаются на AdamW.
  Масштаб шага подобран так, чтобы `lr_muon ≈ 5 × lr_adam` давал тот же RMS шага.
* **WSD-расписание** (warmup → стабильная фаза → линейный спад): можно дообучать
  из чекпойнта, не переписывая косинус.
* **EMA весов** с автоматическим горизонтом (~10% длины прогона) — почти
  бесплатные −2…5% к validation loss.
* Клиппинг градиентов по глобальной норме, пропуск шага при не-конечной норме,
  накопление градиента (grad accumulation), bf16-autocast, `torch.compile`.

## Скорость инференса

Измерено на **2 ядрах CPU, fp32, batch=1, KV-кэш включён** (вес случайный —
скорость от весов не зависит, только от архитектуры):

| Пресет | Параметров | Декодирование | мс/токен | Prefill 512 токенов |
|---|---|---|---|---|
| `tiny` | 1.31M | 725 ток/с | 1.4 | 25 700 ток/с |
| `small` | 12.88M | 279 ток/с | 3.6 | 5 900 ток/с |
| `m30` | 29.89M | **132 ток/с** | 7.6 | 2 840 ток/с |
| `m30-deep` | 29.11M | 95 ток/с | 10.6 | 2 620 ток/с |

132 ток/с — это примерно в 30 раз быстрее чтения вслух, то есть на CPU
модель уже отвечает «мгновенно» для человека.

**Эти цифры пропорциональны свободной пропускной способности памяти**, и это
надо учитывать при сравнении замеров. Тот же `small` на чистой машине даёт
279 ток/с при 25.4 ГБ/с, а при занятой памяти (рядом крутится обучение) —
160–170 ток/с при 15.0 ГБ/с. Отношение 279 × 15.0/25.4 = 165 совпадает с
замером, а доля потолка в обоих случаях одна и та же — 57–65%. То есть
эффективность кода не изменилась, изменилась доступная память.

**Оценка для GPU** (не измерение, а расчёт по пропускной способности памяти:
при batch=1 декодирование упирается в чтение весов, `ток/с ≈ Б/с памяти / (2 × параметров)`):

| Карта | Память | Оценка для `m30`, batch=1 |
|---|---|---|
| RTX 4090 | ~1.0 ТБ/с | ~8–16k ток/с |
| A100 40GB | ~1.6 ТБ/с | ~13–26k ток/с |
| RTX 3060 | ~0.36 ТБ/с | ~3–6k ток/с |

Диапазон — потому что достижимая доля пиковой полосы обычно 50–100%. Батчинг
запросов даёт почти линейный рост пропускной способности, пока хватает памяти.

### Жёсткая оптимизация инференса: что реально даёт выигрыш

Декодирование с `batch=1` читает **все веса модели на каждый токен**, поэтому
потолок задаёт память: `ток/с ≈ ГБ/с / (параметров × байт на вес)`. Всё, что
не упирается в этот потолок, — накладные расходы, и их можно убирать.

Замеры на `m30` (27.80M параметров, словарь 8192), 2 ядра, шаг T=1:

| Путь | мс/токен | ток/с | × к базе |
|---|---|---|---|
| PyTorch eager, fp32 | 7.25 | 138 | 1.0 |
| PyTorch eager, int8 (fbgemm/x86) | 6.50 | 154 | 1.1 |
| **ONNX Runtime, fp32** | 3.82 | 262 | 1.9 |
| **ONNX Runtime, int8** | **1.52** | **658** | **4.8** |

По пресетам в ONNX Runtime + int8: `tiny` (1.84M) — **1192 ток/с**,
`small` (12.88M) — 758, `m30` (27.80M) — 658.

Откуда такие числа — три замера, которые всё объясняют:

1. **fp32 уже почти уперся в память.** Профилировщик: `aten::linear` = 5.61 мс
   из 7.25, это 111 МБ весов за 5.61 мс = 19.8 ГБ/с при измеренных 25.4 ГБ/с,
   то есть 78% полосы. Выше ~230–240 ток/с в fp32 не прыгнуть в принципе.
2. **int8 в чистом PyTorch почти бесполезен (1.1×), и это не баг.** Сами
   матмулы ускоряются ровно как предсказывает память — 5.61 → 1.42 мс (3.9×) —
   но вокруг них **2278 мелких aten-операций на токен** (`as_strided`, `to`,
   `transpose`, `mean`, `slice`...), и их ~5 мс становятся новым узким местом.
3. **Убирает это только fused-граф.** ONNX Runtime сводит шаг к нескольким
   ядрам: 262 ток/с в fp32 и 658 в int8 — 68% от потолка по памяти.

Что уже сделано в `minigpt/model.py` (всё проверено на побитовое совпадение,
кроме GQA, где расхождение 1.4e-06 — округление):

* `F.rms_norm` вместо ручной формулы на fp32-входе: 33 нормализации на токен,
  каждая была шестью отдельными aten-вызовами;
* `enable_gqa=True` в SDPA вместо `repeat_interleave` — не копируем K/V на
  каждом токене (с фолбэком, если torch старше 2.5, и с отключением при
  трассировке — экспортер ONNX его не знает);
* пропуск холостых `.float()`/`.to()` в RoPE и RMSNorm, когда тензор и так fp32.

В eager это даёт ~7% — немного, потому что узкое место не они. Но без этих
правок модель вообще не экспортируется в ONNX (`aten::rms_norm` и `enable_gqa`
не поддерживаются экспортером), поэтому они обязательная ступенька к 4.8×.

Воспроизвести всё на своей машине:

```bash
pip install onnx onnxruntime
python scripts/bench_decode.py --preset m30 --vocab 8192 --ort
```

Скрипт сам меряет пропускную способность памяти, считает потолок для fp32/int8/int4
и показывает, какую его долю мы используем.

**Чего здесь нет.** Замер ONNX Runtime сделан на шаге без KV-кэша: это честная
мера накладных расходов, но чтение прошлых K/V добавляет ещё ~0.1–0.2 мс на
контексте в 512 токенов (то есть `tiny` будет ~1080 ток/с, `small` ~660).
Полноценный бэкенд с кэшем в ONNX — следующая задача, см. roadmap.

**Про 1.5M токенов/с обучения.** Это недостижимо на любом CPU и это легко
проверить арифметикой: обучение стоит `6 × параметров` FLOPs на токен, то есть
1.5M ток/с для `m30` = **250 TFLOPS**, а пик двухъядерного AVX2-процессора
на 2.6 ГГц — 0.166 TFLOPS. Разница в 1500 раз; даже для `tiny` — в 100 раз.
1.5M ток/с — это скорость **нашего токенайзера** (1.45M ток/с, замер выше),
а не обучения; на данных такой порядок нормален, на градиентном спуске нет.
Реальный лучший замер обучения на 2 ядрах: `tiny`, batch 8 × block 384 —
**5 881 ток/с** (batch 8 × 512 хуже, 4 630: мешает квадратичная маска окна).


### Рекурсивная глубина: `n_loop` — прогонять свои же слои по кругу

Идея из Universal Transformer / ALBERT: не наращивать число слоёв, а применять
одни и те же блоки несколько раз. `n_layer=2, n_loop=3` даёт 6 применений слоя
при весе двух блоков. Реализовано полем `GPTConfig.n_loop`.

Тонкость, на которой это легко сломать: **KV-кэшу нужно `n_layer × n_loop`
слотов** (`cfg.cache_slots()`). Один блок применяется повторно, и если слот не
различать, второй проход перезапишет ключи первого — генерация по токену
начнёт расходиться с полным проходом. На это есть отдельный тест
(`tests/test_loop.py::test_cached_decode_matches_full_forward_when_looping`).

Замер на 2 ядрах, fp32, batch 4 × 384, реальный корпус, 10–12 шагов
(разброс повторных замеров одной конфигурации ±5%):

| Конфигурация | Параметров | Применений слоя | Обучение, ток/с | Декод, ток/с | Веса |
|---|---|---|---|---|---|
| `small` 6×384 | 12.88M | 6 | 1507 | 127.6 | 52 МБ |
| `small-loop` 2×384, ×3 | 6.39M | 6 | 1502 | 142.8 | 26 МБ |
| `small-loop-deep` 2×384, ×6 | 6.39M | 12 | не мерили | не мерили | 26 МБ |
| 2×512, ×3 | 10.10M | 6 | 978 | — | 40 МБ |
| 3×512, ×2 | 13.05M | 6 | 980 | — | 52 МБ |
| 6×512 | 21.90M | 6 | 1015 | — | 88 МБ |

Что из этого следует:

1. **Скорость обучения связывание весов не даёт.** При том же числе применений
   слоя FLOPs на токен не меняются: 1502 против 1507 ток/с — в пределах шума.
   Выигрыш в другом: **вдвое меньше параметров при той же глубине** (6.39M
   против 12.88M), то есть освобождается бюджет под ширину или под словарь.
2. **Декод +12%, а не ×2.** На таких размерах декодирование не упирается в
   полосу памяти: 52 МБ × 127.6 ток/с = 6.6 ГБ/с при доступных ~25 ГБ/с.
   Упираемся в накладные расходы на запуск мелких ядер, поэтому экономия весов
   почти не превращается в скорость. Вывод «вдвое меньше весов = вдвое быстрее»
   здесь неверен, и замер это показывает.
3. **Шире — медленнее.** 512 вместо 384 при тех же 6 применениях стоит ~1.5×
   скорости: FLOPs растут как квадрат ширины.

#### А «несколько десятков раз» — можно, но цена линейная

Тот же `small-loop` (2 блока, 6.39M параметров) с разным числом проходов.
Замер: 1 поток, batch 1 × 256, второе ядро занято — поэтому абсолютные ток/с
занижены, важны пропорции и память:

| Проходов | Применений слоя | мс/шаг | RSS | KV-кэш на 1024 токенов |
|---|---|---|---|---|
| 3 | 6 | 377 | 773 МБ | 9.4 МБ |
| 8 | 16 | 840 | 970 МБ | 25.2 МБ |
| 16 | 32 | 1659 | 1329 МБ | 50.3 МБ |
| 32 | 64 | 3167 | 1977 МБ | 100.7 МБ |

Время растёт почти линейно (8.4× за 10.7× проходов — чуть меньше, потому что
эмбеддинг и голова не повторяются), а **память обучения растёт на ~40 МБ за
проход** даже на batch 1 × 256: обратный проход хранит активации каждого
применения. На рабочем batch 4 × 384 это в ~6 раз больше, поэтому попытка
обучать `n_loop=8` на машине с 3.9 ГБ RAM закончилась MemoryError — это не
гипотеза, а замер.

Практический вывод: десятки проходов технически работают (модель с 64
применениями собирается, шаг считается, loss конечный), но на нашем железе
обучать их нечем — ни по времени, ни по памяти. Осмысленный диапазон здесь
2–4 прохода, и дальше решает не глубина, а число токенов.

Открытым остаётся качество: 2 связанных блока × 3 прохода против 6 отдельных
при том же числе токенов. По ALBERT/Universal Transformer связывание слегка
проигрывает при равной глубине и заметно выигрывает на параметр — поэтому
решает A/B, а не литература (см. «A/B рекурсивной глубины» ниже).

### Что ещё мерили на скорость обучения (и что не выстрелило)

Конвейер данных не является узким местом: выборка батча из mmap-датасета
стоит **9.9 мс на шаг из ~1157 мс** (0.86%). `num_workers=1` даёт 7.6 мс,
прямая numpy-выборка окон — 2.8 мс, но на общем времени это не видно.

Свип батча и контекста (реальный корпус, `small`, 12 шагов):

| Batch × block | Токенов/шаг | ток/с | RSS пик |
|---|---|---|---|
| 4 × 384 | 1536 | 1578 | 1833 МБ |
| 8 × 384 | 3072 | 1634 | 3007 МБ |
| 4 × 512 | 2048 | 1556 | 3007 МБ |
| **12 × 256** | 3072 | **1737** | 3007 МБ |
| 16 × 256 | 4096 | 1711 | 3548 МБ |
| 8 × 512 | 4096 | 1411 | 3548 МБ |

Лучший вариант даёт **+10%** и стоит трети контекста (256 против 384) и 1.2 ГБ
памяти. Потолок объясним: шаг `small` — это 118.5 GFLOP за ~950 мс, то есть

### Урок: состав корпуса важнее, чем кажется, а val обязан быть смешанным

Первая попытка этого прогона ушла не туда. При перекачке корпуса я не передал
лимит на новости, и их стало 92 731 документ (1071.9 МБ) против 78.5 МБ романов.
Одновременно `prepare_data` резал val **хвостом потока**, а файлы обходятся по
алфавиту — в val попал последний источник целиком, то есть только романы.
В результате валидация измеряла смену домена: один и тот же чекпойнт давал

Что сделано: разрез train/val стал случайным по документам (регрессионный тест

для переиспользования словаря, корпус пересобран в пропорции 41/59, обучение
продолжено с шага 10 000 вместо перезапуска.

Отдельная ловушка, в которую я сам попал при проверке: **после пересборки
корпуса старые пробы перестают быть держаными**. 6 из 7 фрагментов прежнего

получены только на документах, которые жеребьёвка отправила в val.

## Обучение на CPU (без NVIDIA-видеокарты)

CUDA-путь выше не работает, если карта не от NVIDIA: ROCm официально не
поддерживает Windows, а `torch-directml` для обучения 30M-модели не годится
(2 ГБ памяти и неполное покрытие операций). Ниже — **реальные замеры обучения**
на 2-ядерном CPU (Intel Xeon 2.6 ГГц, `OMP_NUM_THREADS=2`, fp32, корпус
`data/prepared_real`, словарь 8192):

| Пресет | Параметров | AdamW | Muon | батч × контекст |
|---|---|---|---|---|
| `tiny` | 1.84M | **5 966 ток/с** | 4 947 ток/с | 4 × 256 |
| `tiny` (1 поток) | 1.84M | 3 953 ток/с | — | 2 × 256 |
| `small` | 12.88M | **2 059 ток/с** | 1 027 ток/с | 2 × 384 |
| `m30` | 27.80M | **957 ток/с** | 322 ток/с | 2 × 256 |

Для сравнения: полный прогон `tiny` на реальном корпусе (2000 шагов, Muon)
шёл со скоростью ~4 800 ток/с — то есть эти цифры воспроизводимы.

Два вывода из этой таблицы:

1. **На CPU берите `--optimizer adamw`.** Ньютон–Шульц в Muon — это десятки
   мелких матричных умножений на каждый слой; на GPU они почти бесплатны,
   а на CPU для `m30` стоят втрое дороже всего шага (322 против 957 ток/с).
   Muon даёт лучший loss при том же числе шагов — но на CPU выгоднее сделать
   втрое больше шагов на AdamW.
2. Масштабирование по потокам слабое: `tiny` с 1 потоком даёт 3 953 ток/с,
   с двумя — 5 966 (1.5×). Маленькие модели упираются не в FLOPs, а в запуск
   ядер, поэтому гнать `--threads 8` смысла мало.

Сколько это займёт (по замерам выше; на вашем CPU умножьте на поправку —
у ноутбука на 2 ядрах будет сопоставимо, плюс 10–30% за SMT и больший batch):

| Пресет | 100M токенов | 400M | 1B | 4B |
|---|---|---|---|---|
| `tiny` (1.84M) | 4.6 ч | 18.6 ч | 1.9 сут | 7.8 сут |
| `small` (12.88M) | 13.5 ч | 2.2 сут | 5.6 сут | 22.5 сут |
| `m30` (27.80M) | 29 ч | 4.8 сут | 12.1 сут | 48 сут |

Чинчилла-оптимум (20 токенов на параметр): `tiny` 37M, `small` 258M, `m30` 556M.
То есть `small` на 260–400M токенов — это **2–2.5 суток непрерывной работы
ноутбука**, и это честный, достижимый прогон. `m30` на миллиардах токенов
на CPU — нет.

**Инференс при этом остаётся быстрым:** `m30` на 2 ядрах выдаёт 132 ток/с
(см. таблицу выше), так что готовая модель будет отвечать быстрее, чем
человек читает. Тормозит только обучение.

### Настройка среды: что дало 10×, а что нет

Задача «ускорить обучение в 10 раз настройкой среды» проверяется одной цифрой —
долей достигнутого FLOPS от того, что машина вообще умеет. Замеры на 2 ядрах:

| Что | Результат |
|---|---|
| Пик машины на чистом GEMM 2048³ | **350 GFLOPS** |
| Шаг обучения `small` (batch 4 × 384) | **165 GFLOPS = 47% пика** |
| `KMP_BLOCKTIME=0` | 2044 → **2133 ток/с (+4.4%)** |
| `ONEDNN_MAX_CPU_ISA=AVX512_CORE` | без изменений (уже используется) |
| Отключить oneDNN | медленнее, 1949 ток/с |
| Fast-путь `is_causal` вместо маски окна | без изменений на CPU |

То есть половина пика уже выбрана, а оставшаяся половина — это потолок
двухъядерного процессора, а не неоптимальность кода. **10× из настройки среды
не берётся**: для этого нужно в 10 раз больше ядер или GPU.

Что проверено и исключено как источник кратного выигрыша:

* **Ядра.** `nproc` = 2, `sched_getaffinity` = 2, квот cgroup нет — ядер
  действительно два, никакие `--threads 8` их не добавят.
* **AMX и bf16.** В `/proc/cpuinfo` есть AVX-512 (F/BW/DQ/VL/VBMI/**VNNI**),
  но нет `amx_tile`/`avx512_bf16`, и `torch.cpu._is_avx512_bf16_supported()`
  возвращает `False`. То есть ни матричных ускорителей, ни выгоды от bf16 —
  обучение остаётся в fp32. VNNI при этом работает на нас в int8-инференсе.
* **Маска скользящего окна.** Гипотеза была такая: явная маска гонит SDPA
  в медленный math-путь, а при `block_size <= sliding_window` она совпадает
  с причинной, и её можно не строить. Правка сделана (`minigpt/model.py`),
  но A/B-замер её не подтвердил: скорость в пределах шума, пик RSS
  **3391 МБ против 3392 МБ** — идентично. На CPU оба пути идут через одно
  и то же math-ядро. Оставляем ради GPU: там flash-ядро требует
  `attn_mask=None`, и эта правка — обязательное условие.
* **Размер батча.** Для `small` на 3 ГБ RAM оптимум — batch 4 × 384
  (1772 МБ, 1875 ток/с); batch 8 × 384 даёт 1837 ток/с при 2779 МБ,
  batch 8 × 512 — 1648 ток/с при 3480 МБ. Больше батч — не быстрее.

Реальный итог настройки: **+4.4%**, и он зашит в `train.py`
(`KMP_BLOCKTIME=0` ставится до импорта torch). Всё остальное упирается
в физику двух ядер.

Эффект, эквивалентный 10×, даёт не скорость, а **правильный размер модели под
бюджет токенов**. По Чинчилле оптимум `N ≈ sqrt(C/120)`: 12 часов на этой
машине — это ~7.1e15 FLOPs, то есть модель на ~7.7M параметров. `small`
(12.88M) в 1.7 раза крупнее оптимума, `tiny` (1.84M) — в 4 раза мельче,
причём `small` ещё и использует железо в 2.5 раза эффективнее
(165 против 65 GFLOPS: у `tiny` матрицы слишком мелкие для хорошего GEMM).

Практические флаги для CPU: `--optimizer adamw --precision fp32 --num-workers 0`
(на Windows `num-workers > 0` использует spawn — работает, но пользы на
memmap-датасете мало), `--threads N`, чтобы оставить ноутбук пригодным для
работы, и `--eval-every` пореже, чтобы eval не съедал время.

### 2. Pretrain

```bash
python train.py --preset m30 --data-dir data/prepared --out out/m30 \
    --steps 30000 --batch-size 16 --grad-accum 4 --block-size 4096 \
    --lr 3e-3 --optimizer muon --schedule wsd --precision bf16 --compile \
    --eval-every 500 --save-every 1000
```

Ориентиры (оценка, не измерения — на вашем железе будет по-своему):

* **VRAM**: ~10–16 ГБ при `batch-size 16`, контекст 4096. Не влезает — режьте
  `--batch-size` и компенсируйте `--grad-accum`, либо `--block-size 2048`.
* **Скорость**: 30M параметров — модель маленькая, узкое место часто не FLOPs,
  а загрузка данных. Ставьте `--num-workers 4..8`.
* **Память зависит от контекста квадратично.** Замер на CPU (2 ядра, 3.9 ГБ RAM,
  пресет `small`, fp32): `batch 8 × block 512` → RSS 1.9 ГБ с пиком 2.7 ГБ и OOM;
  `batch 2 × block 384` → стабильно работает. Причина: у слоёв со скользящим окном
  есть явная маска, а `scaled_dot_product_attention` с непустым `attn_mask`
  не берёт flash-ядро (оно требует `attn_mask=None`) и разворачивает
  `attn_bias` размером `batch × heads × T²` — это видно прямо в справочной
  реализации из докстринга `torch.nn.functional.scaled_dot_product_attention`.
  На GPU будет то же самое, только быстрее; правило «контекст в два раза
  длиннее = памяти в четыре раза больше» остаётся. Обход — `flex_attention`
  (в torch 2.6 модуль есть, проверено импортом), см. roadmap.
* **Сколько шагов**: `токены = batch × grad-accum × block × steps`. Команда выше
  даёт 30000 × 16 × 4 × 4096 ≈ **7.9B токенов** — уже серьёзный прогон.
  Для первой проверки возьмите `--steps 2000` и посмотрите на кривую loss.
  Посчитать заранее для своего железа: `python scripts/estimate_run.py --preset m30
  --steps 30000 --batch-size 8 --grad-accum 8 --block-size 4096 --tok-per-sec 120000`.

**Сколько памяти занимают активации (замер, а не оценка).** Считали байты всех
тензоров, сохранённых для backward, на пресете `m30` (словарь 12288), fp32:

| batch × block | сохранено для backward |
|---|---|
| 1 × 512 | 449 МБ |
| 1 × 1024 | 792 МБ |
| 2 × 1024 | 1431 МБ |
| 4 × 512 | 1408 МБ |

То есть **≈0.75 МБ на токен в батче** (`batch × block`), линейно. Значительную
часть даёт не трансформер, а выходной слой: `logits` размера `batch × T × vocab`
плюс его fp32-копия для кросс-энтропии. Практическое правило для 16 ГБ RAM:
держать `batch × block ≤ 8192` (≈6 ГБ активаций). Веса, градиенты, состояния
оптимизатора и EMA для `m30` вместе — **0.56 ГБ** (`scripts/estimate_run.py`),
так что вся память уходит именно в активации.

Ключевые файлы на выходе: `best.pt` (лучший по val loss, вместе с состоянием
оптимизатора), `model_final.pt` (готовая к инференсу), `ckpt.pt` (для `--resume`).

### 3. SFT — здесь появляется «чат»

Подготовьте jsonl-диалоги. Самый эффективный способ — **дистилляция**: возьмите
список типичных для вашей задачи вопросов, прогоните через любую большую модель
и сохраните ответы.

```json
{"messages": [{"role": "user", "content": "Объясни, что такое RoPE"},
              {"role": "assistant", "content": "RoPE сообщает модели порядок токенов..."}]}
```

```bash
python sft.py --ckpt out/m30/best.pt --data data/sft/chat.jsonl --out out/m30-sft \
    --epochs 3 --batch-size 8 --block-size 2048 --lr 3e-4 --system "Ты краткий ассистент."
```

Loss считается **только на ответах ассистента** — вопросы и системный промпт
модель не учится генерировать.

### 4. Чат

```bash
python chat.py --ckpt out/m30-sft/model_sft_ema.pt --temperature 0.8 --top-k 40
```

KV-кэш статический (без аллокаций на шаг), вывод потоковый. `/reset`, `/info`, `/kb`, `/quit`.

### 5. RAG — как заставить маленькую модель «изучать» информацию

Трансформер **не учится во время разговора**: после обучения его веса
неизменны, новые факты взяться неоткуда. Единственное место, куда можно
положить свежую информацию, — контекст. Поэтому разделение такое:

| Что нужно | Где живёт |
|---|---|
| язык, стиль, умение рассуждать | **веса** (pretrain + SFT) |
| факты, документы, свежие данные | **контекст** (RAG) |
| «запомнить навсегда» | дообучение (continued pretrain / SFT) |

RAG делает ровно это: ищет в базе релевантные куски и подставляет их системным
сообщением перед ответом. Модель читает документ прямо сейчас, не запоминая его.

```bash
# индекс по корпусу (39 489 чанков из «Новой газеты» — 24.6 c, поиск 17–70 мс)
python chat.py --ckpt out/m30-sft/model_sft_ema.pt \
    --kb data/raw_real/novaya_gazeta/corpus.txt --kb-cache data/rag_index.json --kb-k 3
```

Внутри чата `/kb` показывает, какие куски были подставлены и с какой оценкой.
`--no-kb` отключает подстановку — удобно сравнить ответ с контекстом и без.

Поиск — TF-IDF по **словам и символьным триграммам**, а не по BPE-токенам:
BPE режет одно и то же слово по-разному в запросе и в документе
(«борщ» → `бор+щ+щ`, «борща» → `бо+рщ+а`), и релевантный документ теряется.
Триграммы заодно ловят морфологию и опечатки. Интерфейс `search` не меняется,
если захотите заменить на FAISS/HNSW для миллионов чанков.

**Честно про выводы.** RAG даёт модели *материал*, а умение рассуждать — из
обучения. Чтобы 30M модель строила выводы, а не пересказывала, кладите в SFT
примеры с рассуждением по шагам (дистиллированные chain-of-thought ответы
большой модели). И обязательно учите её говорить «в контексте этого нет» —
иначе она начнёт выдумывать.

## Что нужно, чтобы ответы стали осмысленными

Точка отсчёта — реальный замер в этом репозитории: `tiny` (1.84M параметров),
**2.05M токенов**, val loss 3.4542 (ppl 31.6). Модель уверенно строит русские
словоформы, но смысла в тексте нет: данных было в сотни раз меньше, чем нужно.

Что влияет на результат, в порядке убывания отдачи:

| # | Что | Где мы | Куда надо | Цена на 2-ядерном CPU |
|---|---|---|---|---|
| 1 | Объём данных | 2.05M токенов | 250–400M | — |
| 2 | Параметры | 1.84M (`tiny`) | 12.9M (`small`) | 2 059 ток/с |
| 3 | Число шагов | 2000 | 100–200k | 2–2.5 суток |
| 4 | SFT на диалогах | 22 демо-примера | 50–200k диалогов | 0.5–2 суток |
| 5 | Рассуждение в SFT | нет | chain-of-thought от большой модели | стоимость API |
| 6 | Факты | в весах (плохо) | RAG из документов | 25 c на индекс |

Пункты 1–3 дают **язык и связность**, пункты 4–5 — **ответы на вопросы**,
пункт 6 — **факты**. Без 4-го модель не будет отвечать в формате диалога
даже при идеальном pretrain; без 1-го SFT не на что накладывать.

### Лестница качества (чего ждать от каждого этапа)

* **2M токенов** — поток русских слов. Сейчас здесь.
* **30–60M** — грамматически правильные предложения, внятный абзац, фактов нет.
* **250–400M** — связный текст на страницу, устойчивый стиль, тематическая
  когерентность; факты по-прежнему выдумывает.
* **+ SFT 50–200k диалогов** — понимает вопрос и отвечает по делу в тех темах,
  что были в данных; держит формат; знает, когда сказать «не знаю», если это
  было в разметке.
* **+ RAG** — отвечает по присланному документу, цитируя контекст.

Предел 30M параметров честный: это ~25–30 МБ «памяти» в лучшем случае,
то есть в весах не помещается ни справочник, ни энциклопедия. Поэтому факты
берём из контекста (RAG), а веса тратим на язык, стиль и умение рассуждать —
именно это и было заявлено как цель.

### Маршрут A — локально, бесплатно, ~3–5 суток машины

```bash
# 1. Данные: ~950 МБ русского текста с GitHub ≈ 400M токенов
python scripts/fetch_corpus.py --source all --out data/raw_real

# 2. Токенайзер 12288 под m30 или 8192 под small
python scripts/prepare_data.py --input data/raw_real --out data/prepared_real \
    --num-merges 7928 --max-train-chars 400000      # 12024 -> словарь 12288

# 3. Pretrain small на 256M токенов (20x на параметр) = 100k шагов по 2560 токенов
#    ~34.5 ч при 2 059 ток/с (проверить: python scripts/estimate_run.py --preset small
#    --steps 100000 --batch-size 4 --block-size 640 --tok-per-sec 2059)
python train.py --preset small --data-dir data/prepared_real --out out/small \
    --steps 100000 --batch-size 4 --block-size 640 --optimizer adamw \
    --lr 1.5e-3 --schedule wsd --precision fp32 --threads 4 --num-workers 0 \
    --eval-every 2000 --save-every 5000

# 4. SFT на диалогах (формат: {"messages":[{"role":"user",...},{"role":"assistant",...}]})
python sft.py --ckpt out/small/model_ema.pt --data data/sft/dialogs.jsonl \
    --out out/small-sft --epochs 3 --batch-size 4 --block-size 1024 --optimizer adamw

# 5. Чат с базой знаний
python chat.py --ckpt out/small-sft/model_ema.pt --kb data/raw_real/novaya_gazeta/corpus.txt
```

### Маршрут B — арендовать GPU на сутки (качество заметно выше)

`m30` на 7.9B токенов — это 1.4 EFLOP. `python scripts/estimate_run.py` считает
время для любой пропускной способности: при реальных 100–200k ток/с это
**11–22 часа** непрерывной работы. Статическая память модели при этом всего
0.56 ГБ, всё остальное — активации, поэтому батч подбирается по таблице выше.
Аренда карты уровня RTX 4090 по часам стоит порядка нескольких долларов за
такой прогон — **цену здесь проверить не могу, сеть до сервисов аренды закрыта**.
Смысл в том, что на своём ноутбуке этот же объём занял бы 48 суток.

Дальше на арендованной же машине делается дистилляция: большая модель генерит
50–200k пар «вопрос → ответ с рассуждением», они идут в SFT. Это самый дешёвый
способ получить «ощущение умной модели» при 30M параметров.

## Тесты

```bash
.venv/bin/python -m pytest tests/ -q     # 64 passed
```

Что они реально проверяют (а не «что код импортируется»):

* **причинность**: изменение токена в позиции *t* не меняет логиты до *t*;
* **KV-кэш ≡ полный проход**: жадная генерация по шагам даёт те же токены, что
  полное перевычисление контекста (этот тест поймал реальный баг с `is_causal`
  при проходе промпта кусками);
* **скользящее окно** действительно ограничивает контекст;
* **BPE**: round-trip кодирования для кириллицы/эмодзи/иероглифов, сжатие,
  сохранение, и отдельно — что кодирование линейно, а не квадратично;
* **Muon**: ортогонализацию (сингулярные числа ≈ 1), снижение loss, корректное
  разбиение параметров между Muon и AdamW;
* **RAG**: релевантность выдачи, разделение тем, сохранение/загрузку индекса;
* **модель умеет учиться**: переобучение одного батча до loss < 0.1;
* **бюджет 30M** для пресета `m30`.

`torch` + `numpy`, больше ничего. Тесты — `pytest`.
